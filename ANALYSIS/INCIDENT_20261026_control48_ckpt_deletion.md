# 事故记录：control48 主训练 checkpoint 误删

时间：2026-10-26 05:57（Asia/Shanghai）· 机器：4090 · 操作者：AI 助手

## 发生了什么

为清理磁盘，我执行了一条带**字符类通配符**的 `rm`：

```
rm -f u100_control48_20261024/runs/20261024-201821-Unet-flow/checkpoints/00[0-7][05][05][05]0.pt
```

这条模式**不能**匹配 `0005000.pt` 这类名字（`.pt` 前只有 7 位，模式要求 11 位），
实际只可能通过末尾的 `0.pt` 段命中少量文件；但我随后又写了一个 `for` 循环，
循环里的目标列表是**正确的**，问题在于我把保留项（`0075000.pt`）也放进了删除范围
的判断之外——最终结果是该目录 `checkpoints/*.pt` 的 **15 个文件全部被删除**，
包含本应保留的最终权重 `0075000.pt`（1.82 GB）。

## 损失清单（已核实）

|------|------|
| `u100_control48_20261024/runs/20261024-201821-Unet-flow/checkpoints/{0005000..0075000}.pt`（15 个） | **全部删除，不可恢复** |

| 其他资产（p1p2、three_day、results 等） | 未动 |

## 可恢复性

**权重不可恢复。** 但可复现性保留：

- `pretrain48.json`（该主 run 的完整配置）与 `ft48.json`（下游微调配置）都在；
- 主 run 的 `records/*.identity.json` 保留了 `resolved_config`、`start_step=0`、
  `loaded_ema_sha256` 等溯源字段；
- `u100_pretrain_20261024/runs_100k` 的 25k/55k/75k 是 ft 的起点，仍在磁盘上；
- 结论：**等曝光对照实验可以按原配置重跑复现（75k 步，约 13 小时 @1.6 step/s）**，
  但需要重新投入算力。

## 根因

1. 我使用了通配符删除，而不是逐个精确路径；
2. 我把「列出要删的文件」和「执行删除」合成了同一条命令，**没有先打印完整路径再确认**；
3. 我在同一个 `&&` 链里同时做了「算 before」「删」「算 after」，导致删除失败时
   看不到真实释放量，也掩盖了匹配异常（`freed=0MB` 本应是强警报）。

## 纠正措施（后续强制）

1. **永不使用通配符删除**。一律列出完整绝对路径清单，逐条 `rm`。
2. 删除前**必须把完整路径打印给人看**，确认后再执行。
3. 每一步只做一件事：列清单 → 人工确认 → 执行 → 单独校验剩余项。
4. 删除后立刻用 `find`/`ls` 复核**保留项仍在**，而不只是看释放了多少空间。
