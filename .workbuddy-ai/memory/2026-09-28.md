## 五、傍晚追加：SkelNet 存废裁定（用户质疑"是否又搞出问题、要不要丢掉"）

### 5.1 又一处真实实现 bug —— 已由并行会话修复（commit `caf2324`）
`dit.py` 里 `DeformSkel` 的**构造+载权发生在 `self.initialize_weights()` 之前**，
而 `_basic_init` 用 `self.apply()` 递归重置**所有 `nn.Linear`**（不止 Conv2d）→
SkelNet 内的 `style_proj / affine / style_off / FiLM` 全被 `xavier_uniform_` 冲成随机噪声。
- 在 `deform_trainable=1` 的 run 里会被梯度"救回来"；但在 **`v24_frozenskel`（冻结+w_deform=0）里被焊死在乱码**。
- 铁证：`style_proj |W|₁` 真值 125.96 vs 污染值 397.99（≈Xavier 期望 396.6）。
- 修复：DeformSkel 构造/载权**移到 `initialize_weights()` 之后** + `_basic_init` 内加守卫跳过 `deform_skel.modules()`。

**我独立验证修复有效**（`tools/diag_skelnet_effective.py`）：
离线 vs 重建模型 `style_proj` Δ<1e-4 / `affine` Δ=0 / `style_off` 相对误差 1.4e-7 → **完整载入**。

### 6.3 解开 section[3] "换 g 输出=0" 之谜 —— 是探针伪影，不是接线缺口
`FinalLayer.linear` 与 `adaLN_modulation[-1]` 在 DiT 里是 **zero-init**（标准做法，输出层清零平滑起步）

g 立刻全面影响输出（`d(out)/d(g)` 1.000）。**结论：v25 的 std-skel 条件通路接线正确。**

### 8.3 可行性实测（CPU，`tools/diag_ctrl_fame_cpu.py`）—— ✅ 通路全通
不碰 GPU（当时 serial 训练占 18G）。结果：
- 主模型重建 **46.5M**，+ctrl 分支共 **82.1M**；

### 8.4 复现必踩的 4 个坑（都已定位）
1. **`image_size`/`vae_downscale` 不在 ckpt args 里** → `build_model_from_args` 退回默认
   (256/4) → latent 64² → `pos_embed` 1024 tokens，而 ckpt 是 256 tokens（latent 32²）。
   **必须显式 `vae_downscale=8`**（sd-vae 是 f8）。这是**静默的 shape 错**。
2. **backbone 必须用 s21 自己的 args 建**，不能用 ctrl ckpt 的 args：
   s21 `char_proj_mode=mlp`，ctrl args 写的是 `ln_only` → 拿 ctrl args 建会
   `char_proj.weight` 缺失 + `char_proj.0/1/3.*` 意外（实测 missing=4 unexpected=6）。
3. **ctrl ckpt 只含 ctrl 分支**（`train_ctrl_only=true`）：其 `ema` 只有 159 个 `ctrl_encoder.*` 键，
   必须与 s21 的 backbone（157 键）**合并**才能推理。
4. **资产已归档 + 路径是旧 `5script/` 布局**，需重映射：
   - `final_skel_latents_fame_1px` → **`data/skel/final_skel_latents_fame_1px_v8`**（存在！）
   - `final_latents_fame` → `data/archive/legacy_latents/final_latents_fame_clean`
   - 主 ckpt `s21_fame_flow_v2/…/0030000.pt`、ctrl ckpt `ctrl_fame_1pix_v1/…/0050000.pt`
   - std-skel 输入（喂我们的 SkelNet）→ `data/archive/legacy_skeletons/std_skel1_latents_fame`
   - eval csv → `data/archive/legacy_csv/eval_fame_strict_clean.csv`

### 8.5 做「把我们的 predskel 扔进去」还缺什么
- 分辨率**对得上**（fame ctrl 与 top10 SkelNet 都是 latent 32×32）✅
- 需：fame eval 的 (书家,字) → 取 `std_skel1_latents_fame` 的 std 骨架 → 过
  `deform_skel_top10_v1.pt`（配 `callig_script_emb_top10.pt` 的 19 槽位风格向量）→ predskel
  → 作为 ctrl 的 `cond` 喂进去。
- **风险**：我们的 SkelNet 是在 **top10 的 std-skel 渲染**上训的，fame 的 std 骨架来源不同
  （`std_skel1` vs `top10_style23/std`）→ 存在**分布偏移**，需先做一次骨架一致性对比再下结论。
- 另注意 fame ctrl 的 `num_calligraphers=1013`（不是 45/23），槽位→callig_id 映射要另查。

→ **"GT skel 喂进去效果超级好" 完全复现**（+0.28 SSIM，MSE 降 82%）。
n=60 vs 100 的子集差异解释了 0.75 vs 0.80 的小差距。
耗时：base 352s + ctrl 939s + decode 74s（ctrl 那轮慢是因为与另一个 CPU 任务抢核）。

### 9.2 ❌ 但两套骨架**不能直接对接** —— 差在**笔画宽度**（不是拓扑）
按 `glyph_id` 对齐（6800 个共同 glyph）解码到 256 墨迹图比 IoU：

| 比较 | 共同 glyph | IoU mean | 前景比 (A:B) |
|---|---|---|---|
| top10 **std** vs fame **std_skel1** | 4345 | **0.069** | 0.0504 : 0.0106 = **4.8×** |
| top10 **GT(aux_skel3)** vs fame **1px GT** ← **真正相关的一对** | 6800 | **0.135** | 0.0487 : 0.0162 = **3.01×** |

判读：fame 的骨架墨迹量稳定只有 top10 的 **1/3 ~ 1/5**；且 16 个抽样里有 10 个 IoU 落在
**0.26~0.30**（≈1/3）—— 这正是"细笔画完全被粗笔画包含"的比值。
→ **同一拓扑，不同笔画宽度**：fame 用 **1px** 骨架，top10 用 **~3px** 骨架。
→ 结论：**不能直接把 top10 SkelNet 的 predskel 塞进 fame ctrl**；需要
① 把 top10 骨架按 1px 重渲染/腐蚀（erode）后再编码，或 ② 在 fame 的 1px 空间重训 SkelNet。

### 9.3 方法论踩坑（重要，避免再犯）
- **按 `character` 字符串分组是错的**：csv 同时有 `character_id` 与 `glyph_id`，
  **同一个字有多个字形变体**，变体骨架不同。按字符串分组会把变体混在一起 → 假阴性。
  必须按 **`glyph_id`** 对齐。（实测：按字分组时"同字恒定"判定失败 1610同/2146不同。）
- **别用 `load_shards()` 全量加载**：38583+51322 个 latent 全读进内存，在 CPU 被占满时
  十几分钟不吐字。改成**只读 `img_ids` 建索引 + 按需懒加载**后，同一检查 **37 秒**跑完。
- **只比 latent cosine 判别力弱**：骨架 latent 稀疏，异字 cosine 都有 0.787；
  必须**解码到墨迹图比 IoU**才有判别力。
