### ★ 显存实测（纠正此前"4096 是上限"的错判）
无梯度检查点、独立进程测峰值（4090 24G）：
- 4096×96 OOM 22.8G / 4096×64 OOM 22.2G / 4096×48 OK 18.6G
- 3072×96 OOM 22.5G / **2048×96 OK 18.2G**
- 前向 `no_grad` @4096×96 单独就 **12.3G**

**根因**：`d1` 在 32×32 全分辨率 ×96ch 下，单个激活张量 = batch×96×1024×4B；
batch 4096 → **1.61GB/张**，反向要存 6–8 张 → 单 d1 ~10GB。
**显存几乎只随 batch 线性，对 width 很不敏感**（96→48 只省 ~5G）。

**已实测无效的省显存手段**：`GELU(inplace=True)`（峰值一模一样，因为 GELU 反向可用输出）、
`bf16 autocast`（GroupNorm/cat 仍 fp32）。

**结论**：width 96 + batch 4096 单次前向在 24G 上放不下。三条出路：降 width（丢 v5 U-Net 暖启动）/
梯度累积 2×2048（**数学等价**，模型只用 GroupNorm 逐样本归一）/ 梯度检查点（用户明确禁止）。
**用户拍板：单次 2048 / width 96。**

### 顺带修掉的两个真 bug（`tools/train_deform_standalone.py`）
1. **`img_loss()` 从未被调用** —— 训练循环里只有一行孤儿注释，`--w-img` 是静默空操作。
2. **`_to_gray` 被 `@torch.no_grad()` 包住** —— 图像 loss 的梯度根本回传不到模型。
   拆成 `_decode_gray(lat, grad=False)`；训练路 `grad=True`；`--w-img>0` 时 VAE 常驻 GPU。

## ★★ 训练速度排查：0.496 → 0.358 s/step（1.39×）

用户质疑："30M 的主网络还 4 steps/s，你 infra 写的什么东西"。查下去确实是真问题。

### 定位（先测不猜）
- **吞吐对 batch 完全线性**（256→2048 都是 ~4100-4600 samples/s）→ 排除 launch 开销 / 分配器压力。
- **算子级 profiler**：`upsample_bilinear2d` 占 **30.2%**（40 次调用、平均 37.3 ms/次）。
- **根因**：torch 2.5 的 **NCHW `upsample_bilinear2d` CUDA 核病态慢**。
  batch 2048：C=192 8×8→16×16 **97.0 ms**；C=96 16×16→32×32 **49.6 ms**。
  两次加起来 147 ms/step，和 profiler 的 149 ms/step 完全对上（≈2 G 元素/s，带宽的 2%）。

### 修复（`src/model/deform_skel.py` 新增 `_up()`）
转 `channels_last` 再插值再转回 → 走另一条向量化核，**42× / 10× 更快**，
数值一致到 2.4e-07（纯 float32 舍入，逐形状验证）。**语义完全不变。**
结果：494 → **353.5 ms/step**，`forward(no_grad)` 255 → 114.9 ms，upsample 从 profile 消失。
真实运行 `step 500`：**248 s → 179 s**，功耗 **272 W → 400 W**（GPU 终于被真正驱动）。

### 已实测无效 / 更差（别再走一遍）
- **固定核 `conv_transpose2d` 替双线性**：快 78× 但**数值不等价** —— `align_corners=False` 的
  双线性权重是**位置相关**的（偶位 0.75/0.25、奇位 0.25/0.75）+ 边界 clamp，均匀 stride-2 核复现不了。
- **整模型 channels_last**：**420 ms，慢 0.84×**。风格是 `style_proj(st).expand(...)` 的跨步视图，
  `cat` 后退回 NCHW → 白付转换。**只有 `_up` 这种局部转换划算。**
- **`cudnn.allow_tf32=False`**：353.5 → 354.0 ms，**无变化**（用户要求关，已关，但要如实说它是 neutral）。
- `GELU(inplace=True)`、`bf16 autocast`：均无变化。

### 剩余瓶颈（下一步线索）
conv bwd 48.6% / conv fwd 16.3% / **nchwToNhwc 13.1%** / groupnorm 12%。
★ **结构性浪费**：`coarse=8` 让 `off_u` 在 32×32 算完立刻降到 8×8 再升回，
U-Net 在 32×32 的计算**信息上被丢掉**；32×32 那几个卷积占 **54% FLOPs**。
把 U-Net 直接做在低分辨率理论上能再快 ~2×，但要改架构。
