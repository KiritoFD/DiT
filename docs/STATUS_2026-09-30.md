## 2. 数据泄漏

### 2.1 泄漏的定义

泄漏发生在 **(字, 书家) 组合** 这一级，**不是** img_id、也不是"字"：

> 评测问的是「这位书家写的这个字，骨架长什么样」，而训练集里**正好有这位书家写的这个字**
> （不同张图）。等于把答案给了模型。

**只按 img_id 或按字去重都查不出来** —— 这是本次最容易踩的坑。
（`src/train/configs/v26_gtskel_clean84.json` 的 `_comment` 里写明了正确做法：
"组合级剔除 eval84 的 84 个 (字,书家) 组合 + img_id"。）

### 2.2 实测

eval84 = `data/top10_style23/gt_skel_eval_strict84` 的 84 条，经
`assets/eval_v13_strict_fixed.csv` 映射 → **84 个互不相同的 (字,书家) 组合**。

| 训练集 | 行数 | eval84 组合命中 | 对应训练行 | 谁在用 |
|---|---|---|---|---|
| `assets/train_top10_style23.csv` | 38583 | **80/84** | 123 | v25 / **v26 主干** |
| `assets/train_top10_style23_minusval.csv` | 34749 | **75/84** | 112 | **w7 SkelNet** |
| `assets/train_top10_style23_minusval_clean84.csv` | 34583 | **0/84** | 0 | clean chain |
| `assets/train_top10_style23_clean84.csv` | 38398 | **0/84** | 0 | clean chain |

| 评测集 | 不同 (字,书家) 组合 | 在训练集里的 |
|---|---|---|
| `assets/eval_top10_seen_20.csv` | 20 | **20（100%）** |
| `assets/eval_v13_strict_fixed.csv` | 248 | 80（32%）｜其中能用的 84 条里 **80（95%）** |

### 2.3 影响

- **所有历史 `strict84` / `seen20` 数字全部作废**（包括 v25 的 0.5814、v26 的 0.8163、
  w7 的 resAlign 0.4008、以及各类 `_calib_*` 读数）。
- "strict" 这个命名是误导的：它**不是**未见过字的测试集。

### 2.4 一个反直觉的观察

w7 SkelNet 在**泄漏集**上训的 best resAlign = 0.4008，在**clean84** 上训的 = 0.3931，
只差 −0.008。说明 SkelNet 的 resAlign 对组合级泄漏**不敏感** —— 与"它没真正在利用记忆"
一致（见 §4）。

## 3. 已修复的 bug

### 3.1 `tools/train_joint_g2img.py: regen_pred_shards`（4 处）

| # | Bug | 后果 | 修法 |
|---|---|---|---|
| 1 | **极性反了**：用 `v = 1.0 - 2.0*img` 重编码 std PNG（墨=+1），而训练数据是 `src/data/vae_io.py:_tf_gray` 的 `arr/127.5-1`（白=+1，墨=−1） | 生成器收到**域外输入** → pred 骨架几乎全垃圾 | 改成 **`v = 2.0*img - 1.0`** |
| 2 | `std84_latents.npz` 缓存是**反的**（mean = −0.2520，正确应 ≈ +0.40），且被无条件复用 | 同上，且改了代码也无效 | 加**极性校验**（mean > 0.1 才用，否则作废重建） |
| 3 | 缺**幅度校准** | pred 骨架曝光偏弱，主干照抄条件曝光 → 生成发淡 | 加 **`--beta 0.634`**：`z = (1−β)·g + β·z_gen` |
| 4 | 独立评测脚本把 set 名写成 `strict84_pred_TEST` | `src/eval/in_mem_eval.py:848` 判定 `_is_pred = name.endswith("_pred")`，后缀是 `_TEST` → **读的还是 GT 骨架目录** → 静默把 oracle 数字当成 pred 数字 | set 名必须以 **`_pred`** 结尾 |

> Bug 1/2 的实测证据：`std84_latents.npz` mean = **−0.2520** vs `shards_std` 同 id
> mean = **+0.3997**，**逐元素相关 −0.657**。
> Bug 4 的证据：修正前后两个 set 的读数**逐位相同**（都是 0.7833）。

### 3.2 `tools/eval_union_ckpt.py`（本次新建，独立评测用）

`tools/train_joint_g2img.py` 没有 `--eval-only`，且 run_dir 带时间戳、resume 只在**新建**的
run_dir 里找 ckpt —— 所以没法直接 resume 到旧 ckpt 再触发 eval。本脚本复刻了
`make_eval_args` / `regen_pred_shards` / `run_eval` 三段，并修掉了下面的坑：

| # | Bug | 修法 |
|---|---|---|
| 5 | std 来源用了 `data/top10_style23/shards_std` —— 它与 eval 集（`data/50k/imgs/` 命名空间）**数字 id 撞号但不是同一张图** → 喂进**别的字**的标准骨架 → 生成出完全不同的字 | 改 **`data/50k_v2_glyph15k/shards_std`**（`tools/gen_predskel_dit.py` 的 `SETS["strict84"]` 一直就是这么配的）。修正后 84/84 命中 |

### 3.3 教训

- **凡是和骨架图打交道的阈值，先确认极性**（墨=暗=负）。
- **数字 id 撞号**是这个仓库的高频陷阱：`data/top10_style23/shards_std`、
  `data/50k_v2_glyph15k/shards_std`、`data/top10_style23/gt_skel_eval_strict84` 属于不同命名空间。
- **判"是不是同一个字"必须看图**。用"解码后墨迹掩膜的 IoU"会误判：pred 与 GT 的
  IoU = 0.0645，而"什么都不做"的 g_std 与 GT 也有 0.0567 —— 区分度极差。

| 条件骨架 | **ssim** | frag | lpips | ink_ssim | tgt_spec | cal_enrich |

- **端到端 2500 步还没改善**（0.5396）。
- `tgt_spec` / `cal_enrich`：std 与 pred 条件都是 ≈0 / 1.34×，只有 GT 条件是 +0.27 / 3.94× ——
  风格专属性完全来自"骨架对不对"。

**肉眼几乎一样**，佐证上述结论。

## 5. 瓶颈定位

```
std 骨架        0.5351
   │  ← 阶段1 应该在这里补 +0.28，实际只补了 +0.005
   ▼
GT 骨架         0.8163
```

**缺口仍然主要在阶段1**（0.6427 → 0.8163 还差 62%），但**不是"阶段1 等于没做"**：
它已经把 +0.2812 的缺口兑现了 +0.1076（38%）。旧结论"缺口 100% 在阶段1"是拿
坏掉的 0.5399 推出来的，见文首更正。

而阶段1 的 flow loss 是**收敛的**
（`logs/v30_w7_clean.log`：flow 0.60 → 0.045），但骨架质量几乎不动 ——
**flow loss 与真实目标脱节**，这是目前唯一的大石头。

一个可能的解释：`gen_sample` 的 bridge 采样（`--bridge-hide-g`，glyph 条件恒零，
字符身份全靠输入 latent 承载）在 eval 时用 25 步、训练时用 8 步，口径可能不一致；
也可能 bridge 的目标/起点定义有问题。**尚未排查。**
