## 1. 基础设施与吞吐调优

### 1.1 先纠正一个环境误判

之前日志反复出现 `规避 torch 2.1.2 percolate_tags 递归爆炸`，容易让人以为 4090 卡在 PyTorch 2.1.2 上、装不了新版。**实际不是**：

```
$ /opt/conda/envs/cu121/bin/python -c "import torch;print(torch.__version__)"
2.5.1+cu121
$ nvidia-smi --query-gpu=driver_version --format=csv,noheader
590.48.01
```

"2.1.2" 是本仓库 `compile` 分支里一条**为了兼容老机器而保留的静态提示字符串**，与运行时真实版本无关。结论：**不需要换环境，也不需要为了装新版 torch 去动 conda**。

### 1.2 REPA cache 异步预取（本阶段主要收益）

REPA 教师特征以 fp16 从 pinned RAM 搬到 GPU，每步约 36 MiB。原实现是**同步 H2D**，主线程在拷贝上阻塞。

改动（`src/utils/dino_cache.py`）：

- `prefetch(img_ids, device)`：把下一步的行索引投递到**独立 CUDA stream**，用双缓冲记录 `torch.cuda.Event`；
- `gather(img_ids, device)`：先等 event 完成再返回本步张量，保证数值与同步路径**逐位一致**；
- `src/loss/repa.py`：修掉 `img=None` 时**即使缓存命中也会绕过查表**的早退逻辑（这是之前 REPA 退化成零张量、触发 `H:288, W:0` 的直接原因）。

对照实测（`scratch/v90_infra_profile_20261017/logs/`，20L×384、`B=192`、`w_repa=0.03`、`compile=default`、各 80 步）：

| 配置 | prefetch | 稳态 step/s | 相对 |
|---|---|---:|---:|
| `repa_sync` | ✗ | 4.25 | — |
| `repa_async` | ✓ | **5.12** | **+20.5%** |

> 口径说明：这里取 step 40/60 两点（step 20 是编译热身，step 80 是收尾，都不计入）。两次 run 除 `repa_cache_prefetch` 外配置完全一致。

顺带解决的两个隐性开销：

- `src/train/std_shape.py`：干净条件张量不再做重复 H2D；
- 稳态 reserved 显存 21.48 GiB → **20.37 GiB**（−1.1 GiB）。

### 1.3 引导编译：能编，但不划算

同一套 20L×384、`B=192`、**`w_repa=0.0`**（注意：这一组没有 REPA，只能彼此比较，不能与 §1.2 的 4.25/5.12 直接对比）：

| 配置 | `compile_mode` | `pattern_matcher` | `fullgraph` | 稳态 step/s |
|---|---|---|---:|---:|
| `fusion_on` | default | on | ✗ | 5.37 |
| `current` | default | legacy | ✗ | 5.40 |
| `guided` | max-autotune-no-cudagraphs | on | ✓ | **5.72** |

三点判读：

1. **`pattern_matcher` 没有收益**（5.37 vs 5.40），还多 ~0.7 GiB 显存 → 维持 `legacy`。
2. **`fullgraph=True` 图捕获干净**，没有 graph break，说明模型本身对编译友好。
3. `guided` 稳态 +5.9%，但 `max-autotune` 的 Triton GEMM 预编译把启动时间拉得很长，且换 batch/shape 就要重编。**默认不启用**，只在"确定要跑满 20 万步、且 shape 锁死"时才值得付这个启动代价。

### 1.4 节点 48 离线重建 DINO cache

48 节点没有外网，直接拉 4090 上 14 GB 的 `feats.f16` 只有 ~500 kB/s（约 8 小时）。改成**在 48 上本地重算**：

| 步骤 | 命令 | 结果 |
|---|---|---|
| ① 源特征 | `tools/build_dino_cache.py` → `data/dino_cache/top10_v1` | 26,002 张 / **31 秒**（853 img/s） |
| ② 扩增 | `tools/dino_expand_top10_aug.py` → `data/dino_cache/top10_aug_v1` | 77,823 行 / 14.2 GiB，`miss=0`、`xcheck_fail=0` |

为此给 `build_dino_cache.py` 补了本地 `torch.hub` 回退（`~/.cache/torch/hub/facebookresearch_dinov2_main` + `dinov2_vits14_pretrain.pth`），并修掉了补丁过程中 `hub_local` 作用域写错的 `NameError`。

训练时 REPA 缓存**命中率 100%**（48 上累计 21,600+ 次调用，`miss_rows=0`）。

### 1.5 显存与 Batch 校准（4090，24 GiB）

## 2. L20（20L × 384）收敛判定

### 2.1 已收敛

`v90A_20L_stdstrong` 于 **17:16 正常跑满 max_steps=200000**，日志 `Done!`，checkpoint 与评测均已落盘。

| step | SSIM ↑ | ink-SSIM ↑ | LPIPS ↓ | MSE ↓ | frag* |
|---:|---:|---:|---:|---:|---:|
| 100k | 0.5520 | 0.4002 | 0.3789 | 0.9544 | 1.9074 |
| 150k | 0.5625 | 0.4081 | 0.3687 | 0.9173 | 2.1240 |
| 170k | 0.5653 | 0.4072 | 0.3656 | 0.9059 | 2.2023 |
| 190k | **0.5674** | **0.4079** | 0.3639 | 0.9002 | 2.1620 |
| 200k | 0.5668 | 0.4066 | **0.3638** | **0.8990** | 2.1584 |

\* `frag` = 生成连通块数 / GT 连通块数，**不是越低越好，理想值接近 1**；>1 表示笔画偏碎。

四条证据说明收敛：

1. 训练速度损失在最后 4 万步只在 **0.271~0.273** 窄区间震荡；
2. `grad-norm` 掉到 0.06~0.17；
3. 170k→200k 的 SSIM 变化量在千分位，且 **190k 达峰后 200k 轻微回落**；
4. 余弦调度末段 LR 已到 `5e-6`（`min_lr_ratio=0.1`）。

**结论：不要加练，也不要把 LR 拉回去。** 已收敛的 adaLN 调制参数和 EMA 缓冲被 LR 突跳冲垮的风险，远大于理论收益；要再上台阶应当加容量，不是回炉学习率。

1. **L20 在 S / HWD-CN / MMD / unseen-Top-1 上确实优于 V84A**，但 **mAP 一直略低**（0.177 vs 0.184）。不能笼统说"风格全面更好"。
2. **L20 的 Top-1 峰值在 160k（29.41%），200k 回落到 27.27%**；unseen-Top-1 同样在 160k 达峰（29.03%）后掉到 20.97%。这说明**风格判别力存在"过训"**，200k 不是风格最优。

**因此 L20 的封版应当按指标分别归档**：SSIM-best = **190k**，风格-best = **160k**，不要只留 200k。

### 3.3 两个关键发现

**发现 A：V84D 的样本效率约为 V84A 的 2.2 倍。**

- SSIM：V84D 在 **25k** 达到 0.5456，V84A 要到 **55k** 才到 0.5469 → **2.2×**。
- LPIPS（独立指标，交叉验证）：V84D@25k = **0.38557**，V84A@50k = **0.38589**，V84A@55k = 0.38446 → 基本对齐在 50~55k → **2.0~2.2×**。
- `frag`：V84D@25k = **1.857**，V84A@50k = **2.32**、@200k = **5.99** → 24L 版本笔画明显更完整。

⚠️ **归因缺口（必须写清楚）**：V84D 相对 V84A 同时变了两件事——**深度 12→24** 和 **打开 REPA**。所以这 2.2× **不能**归给 REPA，也**不能**归给深度，目前只能说"深度+REPA 的组合带来 2.2×"。要把两者拆开，需要补一个单变量 run（见 §4.B1）。

**发现 B：宽度从 384 砍到 256，10k 步内看不出损失。**

- L20-w256 @10k：SSIM **0.5175** / ink-SSIM 0.3750 / LPIPS 0.4208
- L20-h384 @10k：SSIM **0.5177** / ink-SSIM 0.3730 / LPIPS 0.4211

参数量差 55%（24.36M vs 53.88M），早期曲线几乎是同一条。唯一略差的是 `frag`（2.564 vs 2.118）。**这只是 10k 的早期信号，还不能下结论**——宽度的劣势通常在 50k 之后才显现，必须等 200k。

## 4. 下一步方向

### A. 已经在跑，不需要新决策（今晚~明日）

| 时间（预计） | 事件 | 用途 |
|---|---|---|
| 10-18 ~02:50 | 4090：L20-w256 跑满 200k | 判定"宽度是否可以砍半" |
| 10-18 ~18:10 | 48：V84D 跑满 200k | 判定"深度+REPA 能否兼顾 SSIM 与笔画完整" |
| 滚动 | 48：每 5k 一次 in-mem eval | 观察 2.2× 优势是否随训练拉长而收窄 |

**建议在 V84D 到 100k 时插一次离线风格评测**（现在 48 上跑，约占 GPU 2~3 分钟），这样能在跑完前就判断它的风格轴是走 L20 的路（低 frag、高 unseen-Top-1）还是走 V84A 的路（高 SSIM、高 frag）。

### B. 值得补的实验（按性价比排序）

**B1. `12L×512 + REPA`（强烈建议，单变量拆解）**

这是当前最大的归因漏洞。配置与 V84A 完全一致，**只加 `w_repa=0.03` + 本地 dino cache**：

- 若它也能到 ~2× 样本效率 → 说明**REPA 才是主因**，深度是次要的，后续所有模型都应默认开 REPA；
- 若它没有加速 → 说明**深度才是主因**，REPA 只是辅助，那么 24L 的收益主要来自容量，宽度/深度的搜索要继续往上推。

成本很低：58.5M 参数、`B=288`、4090 上约 4.8 step/s，跑到 50k 只要 ~3 小时就能看出趋势。**这是我推荐的下一步第一优先。**

**B2. `24L×256`（约 48M 参数，性价比候选）**

若 B 的 w256 结果证明宽度可砍，且 V84D 证明深度值钱，那么 `24L×256` 就是"深度优先、宽度够用"的最优点。4090 单卡应该在 `B=288` 下能跑（估计 22~23 GiB），需要先做一次 5 步校准。

**B3. 补齐 2×2 矩阵的缺口**

现有：{12L,20L,24L} × {512,384,256} 里只有 4 个点，缺 `12L×256` 与 `16L×384`。只在 B1/B2 出结果后再决定要不要补，避免撒胡椒面。

### C. 风格轴的方法论修正

1. **每个 run 都按 step 存风格评测**，不要只在最后一个 ckpt 上评。L20 的 Top-1 从 29.41%(160k) 掉到 27.27%(200k)，如果只看 200k 就会误判"加深不如原版"。
2. 用 `--save-bank-pack` / `--bank-pack` 把参考库嵌入缓存下来，避免每次重建（现在每次要 35~80 秒）。
3. `eval200fix` 只有 187 字、62 个 unseen，Top-1 的相对波动很容易到 ±3 个百分点。**跨模型比较时，2~3 个点的差异不要当结论**，至少要等扩样本或多次种子。

### D. 风险与需要盯的点

| 风险 | 现状 | 处置 |
|---|---|---|
| 48 显存余量小 | 46.0 / 48 GiB，仅 3.1 GiB | 已把 `in_mem_eval_batch` 降到 32、`vae_batch` 16；若 eval OOM，先降 batch 而不是降分辨率 |
| 48 有轻微 swap | 125 GB RAM，57 used，swap 7G 用了 2G | REPA cache 常驻 14.2 GiB + latents 1.2 GiB；如出现 step/s 抖动，先查 swap 再查 GPU |
| 48 磁盘 79% | 372 GB 可用 | 200k 训练约 40 个 ckpt，注意 `ckpt_keep` |
| V84D 时长 | 剩余 175k 步 / 2.05 step/s ≈ 23.7 小时 | 若要提前拿结论，用 100k 的中期评测，不要中途改 batch（会触发重编译） |
| 风格指标口径 | `frag`、SSIM 在不同数据流下绝对值不同 | 本文所有 SSIM 都来自训练内 in-mem eval 的同一实现；风格表的 S/mAP 来自 `style_eval.py`，两者不可混算 |
