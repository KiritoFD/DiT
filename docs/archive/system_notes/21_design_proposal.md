## 1. 要加什么条件

### 1.1 三个候选

| 条件 | 推理时可得？ | 信息 | 覆盖 | 评价 |
|---|---|---|---|---|
| 骨架（当前） | ❌ 需从目标图抽 | 拓扑结构 | 100% | 只能验证上限，不能真用 |
| **标准字形 latent** | ✅ **只需知道写哪个字** | 结构+笔画粗细 | **53.1%** | **真正可用** |
| 字 ID（DINO CLS） | ✅ | 384 维，有效秩 34 | 100% | 已在用，但信息量不足 |

**关键区别**：骨架必须从目标图抽取 → 推理时拿不到 → 0.80 是「复刻」指标。
标准字形 latent 只需知道「写哪个字」→ **推理时天然可得**。

这是把 0.80 从「复刻」变成「零样本生成」的唯一路径。

### 1.2 为什么标准字形 latent 而不是别的

标准字形 latent 是**标准字体渲染后经 VAE 编码**的 4×32×32 特征：
- 含**笔画粗细**（不只拓扑，比骨架信息完整）
- 与 x latent **同空间同域**（都是 VAE latent 空间）
- 是**空间图**，能提供 AdaLN 给不了的位置信息

覆盖缺口：草 10,910 样本、篆 2,977 样本**零覆盖**（无标准字体），
这些样本 g 会给零张量，模型需自行学会忽略。

### 1.3 我要加的具体改动

**改动 A：逐层注入**（核心）

```python
# 原实现（只在输入层加一次）
x = x + glyph_scale * g_tok
# 之后穿过 12 层 Transformer，每层 x + block(x) 都稀释 g 的贡献

# 改后：每层都注入，与 ControlNet 对齐
for i, block in enumerate(blocks):
    x = block(x, c)
    x = glyph_injections[i](x, g_tok)   # out = x*(1+s) + t
```

复用 `controlnet.ZeroAdaLNInjection`，机制已被 0.7889 验证。

**改动 B：保留输入层 token-add**（关键，不可省略）

见 §3.3 的梯度分析——**没有它，`glyph_embedder` 会被冻死**。

**改动 C（后续）：条件 dropout**

训练时以概率 p 随机 drop 标准字形条件，避免模型「复制」标准字形而丢失书法风格，
同时与 CFG 天然配合。已有 `cond_drop_*` 机制，加一个 `glyph_drop_prob` 即可。

**改动 D（备选，暂不做）：输入通道拼接**

`x = cat([x, g])`，信息在残差流自然传播。但破坏 ckpt 兼容，优先级低于 A。

## 2. 能不能学到「这个字应该怎么写」

### 2.1 直接回答：能，但要看怎么注入

**单层注入存疑**（s23 正在验证）。理由：

12 层 Transformer，每层输出 `x + block(x)`。
输入层注入的 g 信号，相对贡献被后续每层的新增残差**逐层稀释**。
这等于把答案写在第一页，让人翻完整本书再回答。

**逐层注入有把握**。机制与 ControlNet 完全相同，而 ControlNet 已实测：
- SSIM 0.4977 → 0.7889
- SkelIoU 0.0115 → 0.3213

### 2.2 预期效果（分指标）

标准字形条件提供「字形结构」，书家条件提供「风格」，二者解耦。
因此：

| 指标 | 预期 | 说明 |
|---|---|---|
| **字形正确率** | **明显提升** | 这是主要收益 |
| SkelIoU | 提升 | 结构跟随变好 |
| SSIM | **中等提升** | 结构对但风格不匹配，SSIM 会低估 |

**必须用字形正确率判读，不能只看 SSIM**：
SSIM 对「结构对但风格不同」惩罚很重，会低估该方案价值。

### 2.3 已知风险

1. **风格趋同**：若条件太强，生成会像标准字体而非书法。
   → 用改动 C（dropout）缓解，并在推理时插值条件强度。

2. **草/篆无覆盖**：46.9% 样本 g 为零。
   → 模型需学会「g 有效时跟随，g 为零时依赖书家+字条件」。
   → 建议显式标记缺失样本，或用「同字其他书体」借代。

3. **六体的 100% 覆盖是假的**：六体落到有覆盖的书体上，是「借用字形」，
   语义上不等于真正的六体字形。

## 3. 参数与梯度（实测）

### 3.1 参数开销

| 配置 | 参数量 | 增量 |
|---|---:|---:|
| 基线 DiT-2Cond-S/2 | 46,524,177 | — |
| + 6 层注入 | 48,298,257 | **+1,774,080 (+3.81%)** |
| + 12 层注入 | 50,072,337 | +3,548,160 (+7.63%) |

**代价很小**。但注意显存：s23 当前已 19.63G/19.63G 占满，
加 12 层注入需减小 batch（192→128）或开 gradient checkpointing。

### 3.2 梯度为 0 的真相（重要）

我第一次测出所有梯度为 0，你指出"可能是初始化问题"——**你是对的**。

根因在 `dit.py:485-488`：

```python
nn.init.constant_(self.final_layer.linear.weight, 0)   # final_layer 全零
nn.init.constant_(self.final_layer.linear.bias, 0)
```

DiT 的 **adaLN-Zero 标准做法**：让初始输出恒为 0。
于是 `out = final_layer(x, c) ≡ 0`，且 `d(out)/d(上游一切) = 0`。

**在真正的 step 0，任何上游参数梯度都是 0 —— 这是设计使然，不是 bug。**
训练开始后 final_layer 迅速学到非零，梯度随即正常流动。

实测（两种模式）：

| 模式 | A | B(6层) | C(12层) | D(仅注入) |
|---|---:|---:|---:|---:|
| `init`（真实 step 0） | 0 | 0 | 0 | 0 |
| `trained`（训练中期） | 6.08e-2 | 5.55e-2 | 5.36e-2 | **0** |

**判断梯度通路是否健康，必须用训练中期的状态，不能用 step 0。**

### 3.3 逐层注入的梯度机制（关键设计约束）

注入 `out = x*(1+s) + t`，其中 `s,t = W@g_tok + b`，W=0, b=0：

```
d(out)/d(b)      = 1        → bias 立刻有梯度        ✅
d(out)/d(W)      = g_tok    → W 立刻有梯度           ✅
d(out)/d(g_tok)  = W = 0    → 逐层注入路径不给
                              glyph_embedder 梯度     ⚠️
```

这是 ControlNet zero-conv warm-start 的标准行为（先学注入权重，再学控制特征），
对 ControlNet **正确**——它的 ctrl_encoder 是独立大网络，本就要慢慢学。

但 `glyph_embedder` 只是个 Conv2d。**若只靠逐层注入，它会被完全冻住。**

**实测证实**（D 组：scale=0，仅逐层注入）：

```
D: 仅逐层注入 6 层 (scale=0)   glyph_embedder = 0.000000e+00  [无梯度]
   inj[0]: W=1.546e-01 b=4.199e-02     ← 注入权重本身梯度正常
```

**所以必须保留输入层 token-add**：`glyph_scale=0.4` 非零，
`d(out)/d(g_tok) = 0.4` → `glyph_embedder` 从 step 0 就有直通梯度。

### 3.4 顺带修掉的一个 bug

`DiT_2Cond.initialize_weights()` 里的 `self.apply(_basic_init)` 会把
**所有** `nn.Linear`（含新加的注入 proj）重新初始化为 xavier_uniform，
破坏 zero-init 恒等语义。

实测 `max|W| = 0.0722`，正是 xavier 边界 `sqrt(2/(384+768))*sqrt(3) = 0.0722`。

**已在 `initialize_weights` 末尾显式重新置零**（修复后 `max|W,b| = 0.0`）。

> 注：`ControlNetDiT` 没有 `initialize_weights`，所以它的 injections
> 从未被覆盖——**这解释了为什么 ControlNet 的 zero-conv warm-start 一直有效**。
>
> 这个 bug 是"完整读代码"才发现的：只看 `ZeroAdaLNInjection` 的定义会以为它是
> zero-init，但调用链上还有一处全局重初始化。

### 3.5 与 ControlNet 的失效模式对照

仓库里出现过**两次同构的静默失效**：

```
w_glyph_cond:     字典缺失 → 返回零张量 → 条件无效但不报错
ControlNet ckpt:  injections 未加载 → zero-init → cond 短路但不报错
本次新发现:       initialize_weights 覆盖 → zero-init 失效 → 破坏 warm-start
```

共同模式：**零/随机初始化 + 宽松加载 = 静默失效**。
排查「某个条件看起来没用」时，应优先检查这个模式。

## 5. 一句话总结

> **信息量从来不是瓶颈，注入方式才是。**
>
> 给模型 4096 维的空间条件，却只在输入层加一次然后让它穿过 12 层 Transformer，
> 等于把答案写在第一页然后让人翻完整本书再回答。
> ControlNet 做对的不是「提供了更多信息」，而是「每层都提醒一遍」。
>
> 附带教训：**zero-init 不是一次性的构造函数调用，
> 而是需要贯穿整个初始化调用链的约束**——
> 任何一次全局 `apply(init_fn)` 都可能悄悄抹掉它。
