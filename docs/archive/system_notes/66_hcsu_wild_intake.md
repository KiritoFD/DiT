## 1. 解压记录

| 项 | 值 |
|---|---|
| 文件 | `wild.zip` 6.12 GB（由 `wild.zip.001–006` 拼接） |
| 加密 | **WinZip AES**（`compress_type=99`）→ **Python `zipfile` 不支持**，必须用 `7z` |
| 密码 | 用户提供，**已验证有效** |
| 解压 | `7z x` + `LC_ALL=C.UTF-8`，**101 秒**，rc=0，32,287 文件 / 6.3 GB |
| 产物 | `/root/Workspace/xy/HCSU/wild_extract/`（78 个 `书家-书体/` 目录） |

### ⚠ 踩到的两个坑（都值得记）

1. **`unzip -l` 把中文名显示成 `#U9ec4#U5ead#U575a`** —— 那是 Info-ZIP 在非 UTF-8 locale 下的
   转义显示，**不是真实文件名**。`python zipfile.namelist()` 给出的是正确中文
   （zip 的 UTF-8 flag `0x800` 已置位）。别被 `#Uxxxx` 骗去写解码器。
2. **远端 `LANG` 为空 → `LC_CTYPE=POSIX` → `7z` 会把中文目录名写成 `??-?`**。
   第一次解压出来的目录名全毁。必须显式 `LC_ALL=C.UTF-8`。
   （顺带发现：已解压的 `tie/` 目录名就是 mojibake `±╥╦∞┴╝-┐¼`，是之前没设 locale 留下的，**需重解**。）

median 0.194，近空白 1.5%，过密 0.5% —— **质量总体不错**，不是脏数据。

## 4. ⚠ 真正的瓶颈：字体覆盖

我们的 `std_path` 是**对应书体的标准字形骨架**（`tools/build_std_skel_px60.py`）：

```python
SCRIPT_FONT = {
    "楷": ["simkai.ttf", "STKAITI.TTF", "NotoSerifSC-VF.ttf"],
    "行": ["STXINGKA.TTF", "FZSTK.TTF"],
    "隶": ["SIMLI.TTF", "STLITI.TTF"],
}
# fallback: SCRIPT_FONT.get(script, SCRIPT_FONT["楷"])
```

`tools/fonts/` 里**只有 simkai / simli / simhei / STXINGKA 四种** —— **没有草书、篆书字体**。

### 实测渲染覆盖率（书体匹配口径）

| 书体 | 有对应字体？ | (书体,字) 组合 | 样本覆盖 |
|---|---|---|---|
| 楷 | ✓ | 3223/3223 | **8531/8531 = 100.0%** |
| 隶 | ✓ | 2074/2108 | **3551/3591 = 98.9%** |
| 行 | ✓ | 2776/3664 | **8878/10263 = 86.5%** |
| 草 | ✗ | 0/3018 | **0/8273 = 0%** |
| 篆 | ✗ | 0/1269 | **0/1629 = 0%** |
| | | | **合计 20,960 / 32,287** |

### 为什么不能用楷体 fallback

若强行 fallback 楷体，覆盖率是 32,287/32,287（100%）—— **但骨架书体与目标不匹配**：
给草书目标喂楷书形状的骨架。这与数据里其余部分（骨架书体 == 目标书体）**自相矛盾**，
模型无法区分"楷形骨架 → 该出草书"还是"楷形骨架 → 该出楷书"。

要救就得加**书体作为显式条件因子** —— 而那条路你们已经否掉了
（"字体×字是不好的标准，直接用 glyph"）。**所以草/篆在补到字体之前不应纳入。**

### 缺口清单（补字体即可解锁）

| 缺口 | 可解锁 | 需要 |
|---|---|---|
| 草书字体 | **8,273 张** | 一套草书字体（如 方正草书 / 汉仪草书 / 免费草书 TTF） |
| 篆书字体 | **1,629 张** | 一套篆书字体 |
| 行书字体（第 2 套） | 行 缺失的 1,385 张 | STXINGKA 之外的 行书字体（`FZSTK.TTF` 已在候选里但本地没有） |

**总计：补 3 套字体可解锁 11,287 张，32,287 全部可用。**

## 6. 接入需要做什么

### 6.1 预处理管线（每张图）

1. **极性归一化**：边框均值 < 0.5 → `1 - x`
2. **紧裁切 + 居中 + resize 到 256×256**（现有 `final_imgs_256` 的做法）
3. **渲染对应书体的标准骨架** → `std_path`
   （`tools/build_std_skel_px60.py` 已有；需处理"该字体渲染不出来"的样本，
   现有代码是静默 fallback 到下一字体 —— **必须改成显式记录并剔除**，
   否则会混进书体不匹配的骨架，重演 §4 的问题）
4. **ID 分配**：`calligrapher_id` / `script_id` / `character_id` / `glyph_id`
   （新书家/新字需要扩展映射表；`文征明/文徵明` 先归一）
5. **合并进 CSV**，`source` 标记（如 `hcsu_wild_v1`），`aug` 留空

### 6.2 顺带可拿的两份（已下载）

| 包 | 量 | 状态 | 说明 |
|---|---|---|---|
| `tie.zip` | 3,780 张 / 65 目录 | 已解压但**目录名 mojibake** | 墨迹（ink manuscripts）—— **与我们现有数据域最接近**，且**有官方 annotations.json** |
| `bei.zip` | 3,240 张 / 36 目录 | 未解压，**README 密码已验证有效** | 碑刻拓片，反相，有 annotations.json |

两者合计 **7,020 张**，且**有官方标注**（`tie_annotations.json` / `bei_annotations.json`
已在 HF cache 里），比 wild 更省事。**建议一并评估。**

### 6.3 建议顺序

```
① 补字体（草/篆/行各一套）           <- 决定最终能拿多少, 且零训练成本
② 写预处理管线（极性 + 归一化 + 骨架渲染 + 剔除无骨架样本）
③ 先只接 楷/隶/行 的 20,960 张       <- 已验证可用, 不依赖新字体
④ 跑一个 40~100k 的对照              <- 判据: gap 斜率是否下降 + 书家风格分化是否改善
⑤ 字体到位后再加 草/篆 的 11,287 张
```

**为什么值得做**：doc 61 §3.6 已经指出 —— ref 是 245M 参数 × 1.93M 图，我们 37M × 28.5k，
**数据差 68×，参数差 6×**。在这个比例下瓶颈是**数据量**不是表征能力。
而"书家风格过拟合"的根因就是**书家太少**（36 位）。
HCSU 一次补上 +22 位书家 / +20,960 张，是目前性价比最高的一步。

## 6.5 【决定】二值化：必须做

**实测证据：**

| | 灰阶数 min/med/max | 二值占比 | 暗像素 | 均值 |
|---|---|---|---|---|
| 我们 `image_path` | 2 / **2** / 2 | **100%** | 16.6% | 212.6 |
| 我们 `std_path` | 2 / **2** / 2 | **100%** | 1.8% | 250.4 |
| HCSU wild | 2 / **206** / 256 | **8%** | 29.9% | 139.3 |

**我们的数据是纯二值的，HCSU wild 是灰度/彩色扫描 → 必须二值化**，
否则 VAE 会见到它从未见过的输入分布。

**阈值沿用现有管线**：`< 128`
（`tools/build_dataset_px60.py:65` `m = a < 128`；`build_std_skel_px60.py:87` `skeletonize(a < 127)`）。

### 完整预处理配方（照 `build_dataset_px60.py` 的 `SIZE=256, BOX_FRAC=0.88`）

```
1. 转灰度
2. ★ 极性归一化: 边框均值 < 0.5 -> 255 - a        <- 现有管线【没有】这一步
3. 二值化: a < 128
4. 紧裁切 bbox -> 缩放到最长边 = 0.88*256 = 225 -> 居中贴到 256x256 白底
```

### ⚠ 极性归一化必须新写

`tools/build_dataset_px60.py` 的文件头注释里写着 UniCalli 被**整源剔除**的原因之一是
"**另有黑底拓片**" —— 说明**现有管线遇到反相图是"直接丢弃"，从来没有极性处理**。
HCSU wild 有 34.4% 黑底 + 24.3% 灰底（58.7% 反相），不能沿用"丢弃"策略
（那会丢掉一半数据），**必须显式加极性归一化**。

## 6.7 极性判定复核（用户质疑后重测）

用户指出"取样里 wild 极性没问题"，遂用**更硬的判据**复核（旧判据只是"背景亮不亮"的代理）：

| 判据 | 定义 | 判为反相 |
|---|---|---|
| 旧 | 边框均值 < 0.5 | 37.5% |
| **新** | **笔画比背景深还是浅**（`n_light > n_dark`） | **35.9%** |

**两判据一致率 98.3%**（2,500 样本），不一致的 42 张全部是边框均值落在 0.46–0.50 的临界样本
—— 旧判据在那批上会翻车。**结论：~36% 反相是真的，测量无误。**

**但这不是数据质量问题，只是一行 `255 - a`。** 而且我此前报的"75.4% 可用"**算严了** ——
它额外要求"白底 > 0.70"，把**灰色旧纸背景的正相图**误杀了。用"墨点相对各自背景"的正确口径：

**归一化后可用率 = 98.0%**（近空白 0.9%，过密 0.5%）

→ 已把 `tools/binarize_hcsu.py` 的极性判据换成新判据（两侧极端像素都极少时退回边框均值）。

### ⚠⚠ 第三个 bug（最严重）：calligrapher_id 与 base 词表撞车

第一版我把新书家的 id 从 `max(旧 CSV 的 calligrapher_id) + 1 = 9002` 开始分配 ——
**但 base 词表里 9002~9010 已经预留给别的书家了**：

```
base 里 >=9000 的键: {9000:41, 9001:42, 9002:43, ..., 9010:51}
第一版分配的新 id:     9002, 9003, ...        <- 与上面 8 个槽位全部撞车
```

**后果**：13 个新书家里有 8 个**静默拿到了别人的 embedding 槽位**（错标），
而且不报错 —— 又一个静默失效。

**修法**：新 id 必须从**词表已有键的最大值**之后开始：
`next_c = max(max(int(k) for k in map), max(旧 id)) + 1` → 9011。
并加断言：`rows` 里每个书家的 id 都必须在词表里，否则直接 raise。

**另外两个修正**：
- `傅山` 可渲染后只剩 **6 张** → 一并剔除（与沈周一起）
- callig 词表**只从最终 rows 构造**，避免被剔除的书家留下孤儿槽位

### ⚠ 构建过程中发现并修掉的两个 bug（都很隐蔽）

1. **`std_path` 是骨架不是填充字形。** 我第一版照 `render()` 渲染了**填充字形**
   （墨点率 0.1999），而我们的 `std_path` 墨点率是 **0.0384** —— 差 5 倍。
   正确的是 `build_std_skel_px60.py:render_skel`：
   `FONT_SIZE=200` 居中 → `skeletonize(a<127)` → `binary_dilation(ST, 1)` → 二值。
   **自己发明一套渲染方式会得到分布完全不同的 g 条件。**

2. **LANCZOS 缩放会引入抗锯齿灰阶。** 我们的数据是**纯二值**，
   而 resize 后的产物是 256 阶灰度 → **缩放后必须再二值化一次**。

3. 附带：`render_skel` 的字体候选里有 `+ ["simkai.ttf", "simhei.ttf"]` fallback ——
   对 行 会退化成**楷形骨架**（书体不匹配且静默）。新脚本默认**关闭 fallback**
   （`--allow-font-fallback` 可开），宁可少要数据也不要混书体的骨架。

### 值得为这 12 位重训 embedding 表吗？—— 值得，且**零额外成本**

**理由**：
1. **表本身几乎无成本**：`num_calligraphers` 52 → 64，embedding 表
   `[53,128] → [65,128]`，**只多 1,536 个参数**，无过拟合风险。
2. **形状变了 → 不能 resume，但本来就不能**：我们正在切 S/2（h 384 vs 432），
   **v12 本来就是从头训的**。所以这 12 个槽位是**搭车免费**拿到的。
3. **直击诊断出的根因**：doc 54/61 判定"书家风格过拟合"的根因就是
   **只有 36 位书家**（UniCalli 因 bbox 越界被整源剔除，base v2 曾有 90 位）。
   36 → 48 是 +33%。
4. **+5,594 张 = +20% 数据**，且这批数据的价值不止"更多风格" ——
   它们同时训练共享主干，改善的是字形渲染本身。

**代价/风险（要说清）**：
- 新书家平均 **466 张** vs 老书家 **794 张** —— 偏低约 40%。
  风险：新 embedding 训练不足 → 退化成"泛化风格"，反而稀释风格信号。
  **对策：训完检查书家区分度（pairwise cos，doc 46 的方法）。**
- ⚠ **不要和模型改动混在一起**：v12 已在旧数据上跑。干净的做法是
  **v17 = v12 配方 + 新数据**，这样"加数据"的效应可单独归因。

### ⚠ 一个必须知道的后果：**不能 resume 现有 ckpt**

`num_calligraphers` **52 → 64** → `y_callig_embedder.embedding_table` 形状从
`[53, 128]` 变成 `[65, 128]` → 现有 ckpt **形状不匹配，无法直接 resume**
（要么从头训，要么 `strict=False` 接受新行随机初始化）。

**必须在配置里换 `callig_id_map` 为 `assets/callig_id_map_hcsu.json`
并让 `num_calligraphers` 走词表长度** —— 否则新书家的 id 查不到会**静默落到 null**。
（`train.py` 会打印 `[callig-map] 加载词表 ...: num_calligraphers 52 -> 64`，
启动时务必确认这一行。）

## 7. 纪律

1. **别信 README 的"normalized to 256×256"** —— 实测只有 9.7% 是正方形，
   中位数 242×258。文档与实际不符时以实测为准。
2. **字体渲染失败必须显式记录并剔除**，不能静默 fallback。
   现有 `build_std_skel_px60.py` 是 `for f in candidates: try/except: continue`，
   失败会落到 `simkai/simhei` —— 对草/篆就是**书体不匹配的骨架**，是静默错误。
3. **书家名要先归一**（`文征明` / `文徵明`），否则同一人会裂成两个 ID，
   反而加重书家侧的分裂。
4. **补数据是当前最大的单一杠杆**，但**判据仍然是 gap 斜率**，不是 strict 单点
   （n=50 的 MDE ≈ 0.014，见 doc 64 §3）。
