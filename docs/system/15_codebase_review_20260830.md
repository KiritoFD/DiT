# 代码 / 模型 / 文档梳理与问题清单（2026-08-30）

> 背景：s22 诊断实验运行期间，对仓库做了一次系统梳理。
> 目标：找出「为什么事情做不动」的结构性原因，而不只是调参。

## 0. 一句话结论

**有一条本该解决核心问题的路径（标准字形 latent 条件），代码完整、数据齐备，
但因为接线接到了一个不存在的字典版本上，从未真正生效过——而且是静默失效。**

这不是调参问题，是接线 bug。以下按严重性排序。

---

## 1. 代码问题

### P0 — `w_glyph_cond` 接线到失效的 v1 字典，静默返回零张量

**现象链**：

```
latent_dataset.py:49   from src.utils import get_glyph_lookup      # ← v1
   ↓
glyph_latent.py:14     LIB_DIR = .../src/utils/std_glyph_latent    # ← 目录不存在
   ↓
glyph_latent.py:41     if not os.path.isdir(d): continue           # ← 静默跳过
   ↓
latent_dataset.py:286  g_t = torch.zeros(...)   # "缺失给零(保 collate 一致)"
   ↓
dit.py:953             x = x + self.glyph_scale * g_tok            # ← 加了个 0
```

**实测覆盖**（`_check_glyph_lib.py`，fame 训练集 51,322 行）：

| 书体 | 样本 | v1 命中 | v1% | v2 命中 | v2% |
|---|---|---|---|---|---|
| 行 | 14,393 | 0 | **0.0** | 9,370 | 65.1 |
| 楷 | 11,921 | 0 | **0.0** | 7,469 | 62.7 |
| 草 | 10,910 | 0 | **0.0** | 0 | 0.0 |
| 六体 | 9,049 | 0 | **0.0** | 9,048 | 100.0 |
| 篆 | 2,977 | 0 | **0.0** | 0 | 0.0 |
| 隶 | 2,071 | 0 | **0.0** | 1,360 | 65.7 |
| **合计** | **51,322** | **0** | **0.0** | **27,248** | **53.1** |

**v1 命中率是 0.0%**——不是"覆盖不全"，是**完全失效**。

**危害**：这是**静默失败**中最坏的一种。启用 `w_glyph_cond=true` 后：
- 不报错、不警告
- loss 正常下降
- 训练日志一切正常
- 但条件从头到尾是零张量，实验完全无效

如果历史上有人试过这个开关、发现"没效果"而关掉，那次实验的结论是**假的**。
这很可能就是文档里反复出现「零样本根本解法……基础设施已就绪，**只差接线**」
（见 11/12/13 三篇）却始终没有落地的原因——接线是**坏的**，不是**没接**。

**修复**（两步，都很短）：

1. `latent_dataset.py` 改用 `get_glyph_lookup_v2()`（v2 数据存在，覆盖 53.1%）
2. 缺失处理改为**可配置**：默认仍给零以保 collate，但打印一次命中率统计；
   提供 `glyph_cond_strict` 开关，缺失时直接报错而非静默

第 2 步比第 1 步更重要——这类"缺失→零"的静默降级是 bug 温床，
仓库里可能还有别处同样模式。

### P1 — v1 / v2 双版本字典并存，且 v1 已死

| | 文件 | 数据目录 | 书体覆盖 | 状态 |
|---|---|---|---|---|
| v1 | `glyph_latent.py` | `std_glyph_latent` | 楷(0)、隶(4) | **目录不存在，0% 命中** |
| v2 | `glyph_latent_v2.py` | `std_glyph_latent_v2` | 楷(0)、行(3)、隶(4)，6 字体 | 43,755 latents，53.1% 命中 |

v1 是 v2 的子集且已废弃，却仍被 dataset 引用。建议**让 v1 代理到 v2**（保持 API
兼容、一次性消灭误用），或直接删除并修正所有引用点。

### P2 — DINO ckpt 路径少算一级（**已修**，commit `9844b8f`）

`src/loss/losses.py::_default_dino_ckpt()` 位于 `src/loss/`，却只向上两级
（得到 `src/`），注释写"项目根"但实际少一级。后果：本地 DINO ckpt 永远找不到，
**静默回退到 `torch.hub`**（需访问 github，受限机器上会失败）。

即 `w_repa` 若曾被启用，走的都是被墙的那条路径。已改为向上逐层搜索。

### P3 — 根目录临时脚本污染

仓库根目录散落 20+ 个一次性脚本与产物：

```
_check_*.py  _probe_*.py  _debug_*.py  _diag_*.py  _dump_*.py  _inspect_*.py
_verify_*.py _stats_*.py  _launch_*.sh
_archive/  _sync_work/  _gt_cache/
fame_meta.json  skel_bank_std.npz  skel_bank_train.npz  gradio_fame_local.py
final_skel_latents_fame/          ← 数据集目录出现在仓库根
```

问题：
- 无法区分"当前可用工具"与"当时调试用的临时文件"
- `final_skel_latents_fame/` 这类数据目录混在源码树里，容易被误提交或误删
- 新会话难以快速判断哪些能跑

建议：可用工具归入 `tools/`，调试脚本归入 `tools/_scratch/` 并加 `.gitignore`，
数据产物统一放到 `data/` 或远程。

### P4 — eval daemon 需为每个实验手动启动，易漏指标

s22 启动后，GPU 侧生成了 eval 图并写了 `eval_pending_*.json`，但
**没有任何 daemon 监听 `s22_char_embed_only` 目录**（现有 daemon 分别指向
s21 / ctrl_fame_v2 / ctrl_fame_std_v1 / s20_*）。结果是图已经生成、指标一直不出现。

已为 s22 手动启动 daemon 补上。这是流程问题：换新实验名时容易忘记配 daemon，
导致"跑了半天没指标"。建议启动脚本里一并拉起对应 daemon。

## 2. 模型问题

### 2.1 char 条件判别力不足（已证实，见 `14_glyph_condition_probe.md`）

- 库内检索 top-1 **84%**，库外（同字不同书家）**4%** → DINO CLS 编码的是
  "这张图长什么样"，不是"这个字是什么字"
- 有效秩仅 34.1 / 384
- 目检 s21 base 生成图（8 对）：约 **25% 存在明显字形错误**

即 base 的 0.50 **不只是风格/纹理损失，确实包含真实的字形错误**。

### 2.2 标准字形条件从未真正启用

`glyph_embedder`（独立 Conv2d）+ 可学习 `glyph_scale` 的实现是**完整且合理**的
（独立投影而非复用 `x_embedder`，保证 LoRA 模式下 g 信号不被锁死——这个设计是对的）。
但它从未在任何一个真实实验中生效过。所有配置文件均为 `w_glyph_cond: false`。

### 2.3 草 / 篆 / 六体的标准字体缺口

v2 只覆盖楷、行、隶（53.1%）。草 10,910 样本、篆 2,977 样本**零覆盖**。
这与 fame 数据的已知情况一致（草/篆/六体无标准字体）。

注意六体命中 100%（9,048/9,049）——六体的 `script_id` 落到了有覆盖的书体上，
是"借用的字形"，不是真正的六体字形，使用时应留意这个语义偏差。

## 3. 文档问题

### 3.1 "只差接线"的表述具有误导性

11 / 12 / 13 三篇文档都写着「基础设施已就绪，只差接线」。
实际是**接线接到了失效的 v1**，且失效是静默的。

应修正为：「接线指向 v1（`std_glyph_latent`，目录不存在，0% 命中），
需改指 v2（`std_glyph_latent_v2`，53.1% 命中）」。

### 3.2 `13_fame_zero_shot.md` §4 的归因需要修正

文档把 `fame-ctrl-stdskel` 失败归因为「ControlNet 学会门控掉冗余条件」，
解法是「提高 char dropout 逼模型依赖骨架」。

**门控是结果不是原因，且该解法不会生效**。需区分两个指标：

- **跟随度**（输出是否忠实于给定骨架）：已经 0.82–0.87，**不需要救**
- **保真度**（输出是否接近目标图）：受限于骨架携带多少目标信息，
  **提高 dropout 救不了**

提高 char dropout 只会让模型在"骨架 vs char"之间重新分配权重，跟随度↑，
但保真度仍被"预测骨架 ≠ 目标图真实结构"钉死在 ~0.52。

### 3.3 缺少单一"当前状态"入口

17 篇文档，`00_README.md` 的「当前运行」还写着 **s20**，实际已跑到 s22。
建议维护一个 `STATUS.md`（或让 00_README 指向它），只放：当前实验、当前 best
指标、当前已知阻塞项。长文档只做归档。

## 4. 下一步方向（按优先级）

### ① 修 `w_glyph_cond` 接线 → 做 A/B（最高优先）

**理由**：这是唯一直接针对"字形正确"的路径。标准字形 latent 编码的是
**字的形状本身**，而不是全局图像描述子——正好补上 DINO CLS 丢掉的空间结构。
代码完整、数据齐备（53.1% 覆盖），只差把 v1 改成 v2。

**成本**：改 1 行 + 重训一次。
**预期**：楷 / 行 / 隶（占样本 55.5%）的字形正确率应有明显提升。

**风险与应对**：
- 训练/推理条件域必须一致（文档 13 §1.3 已强调）
- 草 / 篆无覆盖 → 缺失样本需明确处理策略（给零 / 用同字他体 / 排除）

### ② s22 结果判读（进行中）

冻结主干只训 char embedding，从 s21 best@27500 续跑。判读标准：

| 结果 | 结论 | 下一步 |
|---|---|---|
| SSIM 明显 ↑ | char embedding 是瓶颈且可解 | 全量重训（解冻表从零训） |
| 基本不动 | char embedding 不是唯一瓶颈 | 转向空间化条件（①） |
| loss ↓ 但 eval 平/降 | 过拟合（每字 10.8 样本 × 384 维） | 不能只解冻 embedding，需结构条件 |

### ③ 草 / 篆覆盖缺口的替代方案

v2 无草 / 篆标准字体。可考虑 **retrieval-based glyph condition**：用 fame
训练集内"同字的其他书家字形"作为参考条件。数据里每个 eval 字平均被 ~17 位
书家写过，这个来源很充足，且天然覆盖所有书体。
（注意：这会引入"抄参考图"的风险，需用不同书家 / 加 dropout 缓解。）

### ④ 评测口径

SSIM 对书法有盲区——"写对但细节不同"和"写错"可能都是 0.5。
建议字形正确率做主指标，SSIM 做副指标。

但**字形正确率的自动化测量目前无解**：
- 训练分类器：每字仅 10.8 样本，欠拟合（已试，差）
- DINO CLS 检索：库外 top-1 仅 4%（见文档 14）

可行替代：**小规模人工目检**（如固定 50 样本，每次实验看同一批），
或训练一个仅在"字形是否匹配"二分类上工作的轻量判别器（而非 4765 类分类）。

### ⑤ 数据规模化

fame 51k / 44 书家 vs 全量 329k / 1000+ 书家。当前 200 斩杀线砍掉了
徐渭、张芝、怀仁、杨凝式等代表性书家。可考虑：全量预训练 + fame 微调。
