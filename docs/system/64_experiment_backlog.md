## 2. 本轮的新证据：S/2 假说在 60k 得到支持

v12（S/2）与 v11（M/2）跑的是**同一批 eval 样本**，可逐样本配对：

| step | strict v11 → v12 | seen v11 → v12 | gap v11 → v12 |
|---|---|---|---|
| 50k | 0.5268 → 0.5281 (+0.0013) | 0.5278 → 0.5136 (−0.0142) | +0.0010 → −0.0145 |
| 55k | 0.5290 → 0.5333 (+0.0043) | 0.5393 → 0.5250 (−0.0143) | +0.0103 → −0.0083 |
| 60k | 0.5324 → **0.5366 (+0.0042)** | 0.5557 → **0.5377 (−0.0180)** | +0.0233 → **+0.0011** |

配对检验（n=50 strict / n=10 seen）：

| | d | se | t | 判定 |
|---|---|---|---|---|
| strict @60k | **+0.0042** | 0.0047 | +0.90 | 不显著，但 50k 起**符号连续为正** |
| seen @60k | **−0.0180** | 0.0074 | **−2.43** | **显著** |

**gap 斜率（40–60k 回归）**：

| | 斜率 /1k | t | n |
|---|---|---|---|
| v11 (M/2) | **+0.00171** | +11.0 | 9 |
| v12 (S/2) | **+0.00083** | +6.5 | 9 |
| **v12 / v11** | **0.48** | | |

**结论**：缩到 S/2 后 —— **记忆（seen）显著减少 −0.018，泛化 gap 增速降到 48%，而 strict 未受损（甚至 +0.004）**。
过拟合假说在 60k 得到支持，换 S 是对的。

⚠ **但 v12 相对 v11 是两个变量叠在一起**（容量 S/M **+** 融合 add→cat+glyph_vec）。
上面这张表**不能归属**。要拆开必须补 v12b / v12c（见 E1/E2）。

## 3. ⚠ 一个必须先解决的方法论问题

**strict n=50 的配对 SE ≈ 0.005 → 80% power 下最小可检出差异（MDE）≈ 0.014。**

而我们关心的效应量是 **+0.004**（v12 vs v11 的 strict 差）—— **在这个样本量下永远检不出**。
这就是为什么每一个单点 strict 比较都是"不显著"。

两条出路（**选第二条，成本为零**）：

1. 加大 eval 样本：strict 50 → 200 才能把 SE 降到 0.0025。成本：eval 时间 ×4。
2. **改用 gap 轨迹回归做主判据**：gap 斜率在 n=9 个 checkpoint 上就有 **t=+11**，
   因为它是**跨 checkpoint 聚合**的量，灵敏度远高于单点比较。

→ **判据纪律：主判据 = gap 斜率（40–100k 回归）；次判据 = strict 与 LPIPS 的水平；
单点 strict 差异只作参考，不用来下结论。**

配一个四元组看板：`strict / seen / gap / lpips`，缺一不可（ssim 单独会撒谎，doc 59）。

## 6. ⚠ 一个待查的性能回归（影响上面所有成本估算）

| | 旧进程（已停 @56.2k） | 新进程（resume @55k） |
|---|---|---|
| Steps/Sec | **5.28** | **3.92**（−26%） |
| Mem | 18.83 G | **20.15 G / 20.30 G**（+1.3 G） |
| GPU 时钟 / 功耗 / 温度 | — | 2730 MHz / 364 W / 66 °C（未撞功耗墙） |
| CPU load | — | 14.3 / 128 核（**非 CPU 瓶颈**） |

已排除的原因：compile 仍生效（`[compile] torch.compile(mode=default)` 在日志里，无 graph break）；
LPIPS 在 CPU 上（`lpips.LPIPS(net="vgg")` 未 `.to(cuda)`，不占显存）。

**最可能的原因：显存逼近上限（20.15/20.30 G）导致 allocator 频繁 `cudaMalloc/free` 同步。**
resume-full 会额外驻留 optimizer state（~292MB）+ fp32 master（~146MB）+ EMA（~146MB），
再加碎片 → +1.3G 把余量吃光。

待验（不停训练的前提下次序）：
1. `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 重启 —— 零风险，一行环境变量
2. 若无效，查 resume 后是否可释放加载用的临时 buffer

**这一项直接决定上面所有"X 小时"的估算**（3.92 vs 5.28 step/s 差 35%）。
建议在做 Tier 1 之前先处理。

## 7. 纪律（固化）

1. **主判据是 gap 斜率，不是单点 strict。** n=50 的 MDE 是 0.014，我们关心的效应是 0.004 —— 单点比较在这个样本量下没有分辨力。
2. **每个实验必须同预算（步数）、同数据、跑到平台。** 80k 下结论已经让我们在 xattn 上打过一次脸。
3. **看四元组 `strict / seen / gap / lpips`。** ssim 单独会撒谎（doc 59，本轮在 15k 又复现一次）。
4. **加组件前先问"这个信号是不是已经从别处给了"。** 12ch / style token / callig_spatial 是同一个错误的三种形态。
5. **减组件前先问"它有没有被单独消融过"。** `glyph_embedder_depth` 就是空白 —— 不能靠"看起来冗余"直接砍。
6. **新增 config 键后确认它出现在 `resolved_config`。** 已踩 4 次（`aux_zero_white` / `image_channels` / `repa_layers` / …）。
